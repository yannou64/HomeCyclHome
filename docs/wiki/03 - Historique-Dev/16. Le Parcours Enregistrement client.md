# 16. Le Parcours Enregistrement Client

**Sprint :** 1 — Authentification  
**Statut :** ✅ Backend complet / 🔄 Frontend en cours

---

## Vue d'ensemble

Le parcours d'enregistrement couvre trois étapes distinctes, chacune correspondant à un endpoint backend et un écran frontend.

```
Visiteur remplit le formulaire
        ↓
POST /auth/register
→ Compte créé (is_actif = false)
→ Email de confirmation envoyé
        ↓
Visiteur clique sur le lien dans l'email
        ↓
GET /auth/confirm-email?token=xxx
→ is_actif = true, token effacé
        ↓
Utilisateur se connecte
        ↓
POST /auth/login
→ Cookies HttpOnly posés (access_token + refresh_token)
→ { userId, role } retourné au frontend
```

---

## Décisions de conception

**Pourquoi confirmer l'email avant de se connecter ?**  
Deux raisons : valider que l'adresse existe réellement, et empêcher quelqu'un d'usurper l'email d'un tiers pour créer un compte.

**Pourquoi `is_actif = false` par défaut ?**  
Le compte est créé immédiatement en base (pour réserver l'email), mais reste inaccessible jusqu'à confirmation. Si l'utilisateur ne confirme pas dans les 48h, le lien expire — il devra refaire une inscription.

**Token de confirmation aléatoire (`crypto.randomBytes`)**  
32 octets en hexadécimal = 64 caractères. Impossible à deviner par force brute. Stocké en base et effacé dès utilisation.
