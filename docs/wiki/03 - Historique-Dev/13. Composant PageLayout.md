# 13. Composant PageLayout

> **Fichiers concernés**
> - `src/shared/components/PageLayout/PageLayout.tsx`
> - `src/shared/components/PageLayout/PageLayout.module.scss`
> - `src/pages/Home.tsx` (utilisation)

---

## Pourquoi ce composant existe

Chaque page de l'application a besoin de la même structure de fond : une image en haut qui fondu, un espace central pour le contenu, et un carousel en bas. Plutôt que de répéter cette structure dans chaque page, on la centralise dans un seul composant de mise en page.

**PageLayout est un composant de "shell"** : il ne contient pas de contenu métier, seulement l'enveloppe visuelle. Le contenu de chaque page arrive via `children`.

Usage dans une page :
```tsx
<PageLayout>
    <MonContenuDePage />
</PageLayout>
```

---

## Structure en 3 bandes (mobile)

```
┌────────────────────┐
│  Image Lyon        │  ← .topSection
│  ░░░ gradient ▓▓▓  │    image + fondu vers le vert menthe
├────────────────────┤
│  {children}        │  ← .contentSection (main)
│  fond vert menthe  │    flex: 1 — s'étire pour remplir l'espace
├────────────────────┤
│  ▓▓▓ gradient ░░░  │  ← .bottomSection
│  Carousel          │    fondu depuis le vert menthe + carousel
└────────────────────┘
```

## Structure en grille 2 colonnes (desktop)

```
┌──────────────┬──────────────┐
│              │  {children}  │
│  Image Lyon  │  centré      │
│  (full       ├──────────────┤
│   height)    │  Carousel    │
└──────────────┴──────────────┘
```

## La technique des CSS Custom Properties pour les images

Les images de fond varient selon le viewport (mobile vs desktop). Plutôt que de les coder en dur dans le SCSS (ce qui rendrait le chemin des fichiers difficile à gérer), on les injecte depuis le composant React via des **CSS Custom Properties** (variables CSS) en `style` inline :

```tsx
<div
    className={styles.topSection}
    style={{
        '--bg-mobile': `url(${fondEcranLyonMobile})`,
        '--bg-desktop': `url(${fondEcranLyonDesktop})`,
    } as React.CSSProperties}
/>
```

Et dans le SCSS, on les consomme :
```scss
.topSection {
    background-image:
        linear-gradient(...),
        var(--bg-mobile);
}

@include desktop {
    .topSection {
        background-image: var(--bg-desktop);
    }
}
```

**Pourquoi ce choix ?** Vite traite les imports d'images en TypeScript et leur assigne un hash de cache au build (`logo.a3f2b1.webp`). En important l'image dans le TSX, Vite génère le bon chemin final. Si on écrivait l'URL directement dans le SCSS, le chemin serait relatif au fichier SCSS et pourrait se casser au build.

## Les dégradés (linear-gradient)

Le fondu entre l'image et le fond vert menthe est produit par **deux couches de background empilées** :

```scss
background-image:
    linear-gradient(to bottom, transparent 40%, #{$color-myLightGreen} 100%),
    var(--bg-mobile);
```

CSS interprète ça de haut en bas : le dégradé est **au-dessus** de l'image. Au-delà de 40% de hauteur, il devient progressivement opaque en vert menthe, masquant l'image en dessous.

**Pourquoi `#{$color-myLightGreen}` et pas `$color-myLightGreen` directement ?**
À l'intérieur d'une fonction CSS comme `linear-gradient()`, SCSS ne sait pas automatiquement qu'il doit interpoler la variable. La syntaxe `#{}` force l'interpolation : SCSS remplace la variable par sa valeur hexadécimale avant de transmettre au navigateur.

Pour la section basse, le dégradé est inversé :
```scss
// ::before pseudo-élément sur .bottomSection
background: linear-gradient(to bottom, #{$color-myLightGreen}, transparent);
```

Le vert menthe part du haut (opaque) et se dissout vers le bas (transparent), révélant le carousel en dessous.

---

## Le pseudo-élément `::before` pour le dégradé bas

```scss
.bottomSection {
    position: relative;
    overflow: hidden;

    &::before {
        content: '';            // obligatoire pour qu'un pseudo-élément existe
        position: absolute;
        top: 0;
        left: 0;
        right: 0;
        height: 55%;
        background: linear-gradient(to bottom, #{$color-myLightGreen}, transparent);
        z-index: 1;
        pointer-events: none;
    }
}
```

**Pourquoi un `::before` plutôt qu'un `<div>` dans le JSX ?**
Un dégradé purement décoratif n'a pas sa place dans le HTML. Les pseudo-éléments sont faits pour ça : ajouter du visuel sans polluer le DOM. Moins de nœuds = meilleure performance et HTML plus propre.

**`pointer-events: none`** est indispensable : le pseudo-élément est positionné en absolu au-dessus du carousel. Sans cette propriété, il bloquerait tous les événements souris/tactiles sur le carousel en dessous.

**`overflow: hidden`** sur `.bottomSection` empêche le carousel (qui peut être plus large que son conteneur) de déborder visuellement.

## La transition mobile → desktop (Flex → Grid)

C'est la partie la plus instructive du composant. Sur mobile, le layout est une colonne flex. Sur desktop, il devient une grille CSS.

```scss
// Mobile (défaut)
.pageLayout {
    display: flex;
    flex-direction: column;
    flex: 1;
}

// Desktop
@include desktop {
    .pageLayout {
        display: grid;
        grid-template-columns: 1fr 1fr;  // deux colonnes égales
        grid-template-rows: 1fr auto;    // ligne haute flexible, ligne basse auto
    }
}
```

**Le placement dans la grille :**
```scss
.topSection  { grid-column: 1; grid-row: 1 / 3; } // colonne gauche, toutes les lignes
.contentSection { grid-column: 2; grid-row: 1; }   // colonne droite, ligne haute
.bottomSection  { grid-column: 2; grid-row: 2; }   // colonne droite, ligne basse
```

`grid-row: 1 / 3` signifie "de la ligne 1 à la ligne 3" (exclusif) — donc l'image Lyon occupe toute la hauteur de la grille, peu importe la hauteur du contenu à droite.

**`flex: 1` sur `.pageLayout` reste valide en desktop.** Il s'applique à `.pageLayout` comme enfant de `#root` (contexte flex), et `display: grid` s'applique à l'intérieur de `.pageLayout`. Les deux niveaux sont indépendants.

## Les images du carousel — données dans le composant parent

```typescript
// PageLayout.tsx
const CAROUSEL_IMAGES = [
    reparationVeloMobile,
    reparationVeloDesktop,
];

// transmises au Carousel
<Carousel images={CAROUSEL_IMAGES} speed={30} />
```

**Pourquoi définir les images dans `PageLayout` et pas dans `Carousel` ?**
Le `Carousel` est un composant générique — il ne sait pas ce qu'il affiche, il sait juste comment faire défiler des images. En séparant les données (ici dans `PageLayout`) du comportement (dans `Carousel`), on rend `Carousel` réutilisable pour n'importe quel contexte.

Si demain une autre page veut un carousel de photos de clients satisfaits, elle peut utiliser le même composant `Carousel` avec ses propres images.

---

## Ce que `PageLayout` ne fait PAS

- Il ne contient pas de logique métier
- Il ne consulte pas le contexte d'authentification
- Il ne décide pas de ce qui s'affiche dans `children`
- Il ne gère pas la navigation

C'est intentionnel : un composant de layout est **agnostique au contenu**. Sa seule question est "comment est organisé l'espace ?", pas "qu'est-ce qui s'affiche ?".
