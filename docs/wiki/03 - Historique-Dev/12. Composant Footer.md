# 12. Composant Footer

> **Fichiers concernés**
> - `src/shared/components/Footer/Footer.tsx`
> - `src/shared/components/Footer/Footer.module.scss`
> - `src/app/styles/_reset.scss` (sticky footer layout)
> - `src/app/styles/_base.scss` (sticky footer layout)

---

## Ce que fait ce composant

Le Footer est un composant purement **présentationnel** : il n'a pas d'état, pas d'effet, pas de props. Il affiche deux choses :
1. Les liens légaux (Mentions légales, CGU, Confidentialité)
2. Le copyright avec l'année courante

---

## L'année dynamique

```typescript
const currentYear = new Date().getFullYear();
// ...
<p className={styles.copyright}>© LeCycleLyonnais {currentYear}</p>
```

`new Date().getFullYear()` retourne l'année en cours sous forme de nombre (ex: `2026`). Ce calcul se fait au moment où le composant se monte — au premier rendu de la page.

**Pourquoi ne pas hardcoder `2026` ?** Parce qu'une valeur hardcodée devient fausse dès le 1er janvier de l'année suivante, et personne ne pense à la mettre à jour. Avec cette approche, c'est automatique et ça ne coûte rien.

---

## Les constantes hors du composant

```typescript
// Défini UNE FOIS au chargement du module, jamais recréé
const LEGAL_LINKS = [
    { label: 'Mentions légales', to: '/mentions-legales' },
    { label: 'CGU', to: '/cgu' },
    { label: 'Confidentialité', to: '/confidentialite' },
];

export function Footer() { ... }
```

Le tableau `LEGAL_LINKS` est défini **en dehors** de la fonction composant. C'est intentionnel.

Si on le définissait à l'intérieur, il serait recréé à chaque re-render du composant (à chaque fois que React redessine le Footer). Ce n'est pas dramatique pour un tableau de 3 éléments, mais c'est une mauvaise habitude : les données statiques n'ont rien à faire dans le cycle de vie d'un composant.

**Règle à retenir :** tout ce qui ne change jamais → constante au niveau du module.

## Le pattern `Fragment` + séparateur

```typescript
import { Fragment } from 'react';

{LEGAL_LINKS.map((link, index) => (
    <Fragment key={link.to}>
        {index > 0 && (
            <span aria-hidden="true" className={styles.separator}>·</span>
        )}
        <Link to={link.to} className={styles.legalLink}>
            {link.label}
        </Link>
    </Fragment>
))}
```

Trois points à comprendre ici :

**1. Pourquoi `Fragment` et pas `<div>` ?**
Quand on `.map()` plusieurs éléments JSX, React exige une racine unique par élément (pour le système de réconciliation). On pourrait utiliser `<div>`, mais cela ajouterait des `<div>` dans le DOM qui cassent le `display: flex` de la nav. `Fragment` est un conteneur "fantôme" — il groupe sans ajouter de nœud DOM.

**2. Pourquoi `key` sur `Fragment` et pas sur `Link` ?**
La prop `key` doit être sur l'élément **racine** de chaque itération. Ici la racine est le `Fragment`, donc `key` va là.

**3. `index > 0` pour éviter le séparateur avant le premier lien**
On ne veut pas `· Mentions légales · CGU · Confidentialité` mais `Mentions légales · CGU · Confidentialité`. La condition `index > 0` insère le séparateur uniquement entre les liens (pas avant le premier).

---

## L'accessibilité du séparateur

```typescript
<span aria-hidden="true" className={styles.separator}>·</span>
```

`aria-hidden="true"` indique aux lecteurs d'écran d'ignorer cet élément. Sans cet attribut, un lecteur d'écran lirait : *"Mentions légales, point médian, CGU, point médian, Confidentialité"* — ce qui est absurde pour quelqu'un qui navigue au clavier.

Avec `aria-hidden`, il lit : *"Mentions légales, CGU, Confidentialité"* — propre.

Le séparateur est aussi marqué `user-select: none` en CSS : il ne sera pas copié si l'utilisateur sélectionne le texte.

---

## La hiérarchie visuelle des couleurs

Le footer utilise trois niveaux d'opacité sur blanc pour créer une hiérarchie discrète :

```scss
.legalLink  { color: rgba(255, 255, 255, 0.75); }  // liens — plus visibles
.separator  { color: rgba(255, 255, 255, 0.40); }  // séparateur — très discret
.copyright  { color: rgba(255, 255, 255, 0.50); }  // copyright — entre les deux
```

**Pourquoi cette approche ?** Parce qu'un footer sur fond sombre avec du texte blanc pur (`#fff`) à 100% d'opacité attire autant l'œil que le contenu principal — ce qu'on ne veut pas. En baissant l'opacité, les informations légales restent lisibles sans "crier".

Les liens passent à `color: white` au hover pour signaler l'interactivité.

---

## Le sticky footer — pourquoi ça se joue dans le layout

Quand on dit "le footer colle en bas", on ne parle pas de `position: sticky`. Ce serait une erreur : `sticky` garderait le footer **toujours visible** à l'écran, par-dessus le contenu au scroll.

Le comportement voulu est différent :
- Si la page est courte → le footer descend jusqu'au bas du viewport
- Si la page est longue → le footer est simplement à la fin du contenu

Ce pattern s'appelle le **sticky footer** et repose sur une chaîne flex du HTML au `<main>` :

```scss
// _reset.scss
body {
    min-height: 100vh;      // le body occupe au moins tout l'écran
    display: flex;
    flex-direction: column;
}

#root {                     // le div racine de React/Vite
    flex: 1;                // s'étire pour remplir le body
    display: flex;
    flex-direction: column;
}

// _base.scss
main {
    flex: 1;                // avale tout l'espace vertical disponible
}                           // → pousse le footer en bas naturellement
```

**La chaîne de responsabilités :**
```
body      (au moins 100vh de haut, flex colonne)
└── #root (s'étire, flex colonne)
    └── <header>  ← hauteur naturelle
    └── <main>    ← prend TOUT l'espace restant
    └── <footer>  ← hauteur naturelle, poussé en bas
```

Le Footer lui-même n'a aucun style de positionnement — c'est son environnement qui le place correctement. C'est un exemple de **séparation des responsabilités** : le composant décrit son apparence, le layout décide de sa position.
