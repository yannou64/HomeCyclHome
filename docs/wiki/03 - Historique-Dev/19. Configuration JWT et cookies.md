# 19. Configuration JWT et Cookies

**Sprint :** 1 — Authentification  
**Fichiers :** `Backend/src/config/jwt.config.ts` · `Backend/src/config/cookie.config.ts`  
**Statut :** ✅ Terminé

---

## Pourquoi deux fichiers de config ?

On centralise les valeurs réutilisées en un seul endroit pour éviter la duplication et garder les secrets lisibles depuis `.env`.

---

## jwt.config.ts

```typescript
import { JwtSignOptions } from '@nestjs/jwt';

export const jwtAccessConfig: JwtSignOptions = {
    secret: process.env.JWT_ACCESS_SECRET as string,
    expiresIn: '15m' as JwtSignOptions['expiresIn'],
};

export const jwtRefreshConfig: JwtSignOptions = {
    secret: process.env.JWT_REFRESH_SECRET as string,
    expiresIn: '7d' as JwtSignOptions['expiresIn'],
};
```

> Le cast `as JwtSignOptions['expiresIn']` est nécessaire car TypeScript infère `'15m'` comme `string` alors que le type attend `StringValue` (type brandé du package `ms`).

## cookie.config.ts

```typescript
import { CookieOptions } from 'express';

export const ACCESS_COOKIE: CookieOptions = {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',
    maxAge: 15 * 60 * 1000, // 15 minutes en ms
};

export const REFRESH_COOKIE: CookieOptions = {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',
    maxAge: 7 * 24 * 60 * 60 * 1000, // 7 jours en ms
    path: '/auth/refresh',
};
```

### Options expliquées

| Option | Rôle |
|---|---|
| `httpOnly: true` | Cookie inaccessible au JavaScript — protection XSS |
| `secure: true` en prod | Cookie transmis uniquement en HTTPS |
| `sameSite: 'strict'` | Cookie non envoyé lors de requêtes cross-site — protection CSRF |
| `path: '/auth/refresh'` | Le refresh token n'est envoyé que vers cet endpoint |

---

## Stratégie des deux tokens

| Token | Durée | Rôle |
|---|---|---|
| `access_token` | 15 min | Prouve l'identité à chaque requête |
| `refresh_token` | 7 jours | Permet d'obtenir un nouvel access token sans se reconnecter |

**Flux :**
```
Login → access (15min) + refresh (7j)
Après 15min → frontend appelle /auth/refresh → nouvel access token
Après 7j sans activité → refresh expiré → reconnexion obligatoire
```

L'utilisateur ne perçoit que la durée du refresh token comme "durée de session". Le renouvellement silencieux de l'access token est une mécanique interne.

> Le endpoint `/auth/refresh` n'est pas implémenté dans ce sprint.
