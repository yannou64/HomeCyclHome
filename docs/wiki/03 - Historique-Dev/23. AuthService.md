# 23. AuthService

**Sprint :** 1 — Authentification
**Statut :** ✅ Terminé, **architecture depuis remplacée**

> ⚠️ **Mise à jour :** ce guide décrit la conception initiale du Sprint 1 — un unique service
> `AuthService` regroupant toute la logique d'authentification. Cette classe n'existe plus :
> le backend a été refactorisé en **Clean Architecture** (un *use case* = une classe = une
> opération métier). Le fichier `Backend/src/features/auth/services/auth.service.ts` n'existe
> plus ; la logique décrite ci-dessous est aujourd'hui répartie dans
> `Backend/src/features/auth/use-cases/{register, confirm-email, login, logout, refresh-token}.use-case.ts`.
> Un sixième use case, `RefreshTokenUseCase`, a été ajouté (`POST /auth/refresh`) et n'existait
> pas à l'écriture de ce guide. Le raisonnement métier ci-dessous (pourquoi hasher le mot de
> passe, pourquoi un message d'erreur générique…) reste valable — seul le découpage en fichiers
> a changé.

---

## Rôle (à l'origine)

C'était la pièce centrale — toute la logique métier de l'authentification. Le controller recevait les requêtes HTTP et déléguait immédiatement à ce service.

Quatre méthodes publiques à l'origine, une cinquième (`refresh`) ajoutée plus tard :

| Méthode d'origine | Use case actuel | Endpoint associé | Description |
|---|---|---|---|
| `register(dto)` | `RegisterUseCase.execute(dto)` | POST /auth/register | Crée le compte, envoie l'email |
| `confirmEmail(token)` | `ConfirmEmailUseCase.execute(token)` | GET /auth/confirm-email | Active le compte |
| `login(dto, res)` | `LoginUseCase.execute(dto)` | POST /auth/login | Vérifie l'identité, génère les tokens (les cookies sont posés dans le controller, plus dans le use case — voir [[24. AuthController]]) |
| `logout(userId, res)` | `LogoutUseCase.execute(userId)` | POST /auth/logout | Invalide le refresh token en base (les cookies sont effacés dans le controller) |
| *(n'existait pas)* | `RefreshTokenUseCase.execute(refreshToken)` | POST /auth/refresh | Vérifie le refresh token, régénère un access token de 15 min |

Chaque use case reçoit désormais `IAuthRepository` (interface, implémentation Prisma injectée) au
lieu d'un `PrismaService` direct — cohérent avec le pattern repository utilisé par les autres
features (voir [[../architecture.md]]).

---

## register()

```
1. Vérifie que l'email n'existe pas → ConflictException (409) si doublon
2. Hash du mot de passe : bcrypt.hash(password, 12)
3. Génère un token : crypto.randomBytes(32).toString('hex')
4. Calcule token_expires_at = now + 48h
5. Crée l'utilisateur en base (is_actif = false)
6. Envoie l'email de confirmation
7. Retourne { message: '...' }
```

## confirmEmail()

```
1. Trouve l'utilisateur par email_confirmation_token
2. Si absent → NotFoundException (404)
3. Si token_expires_at < now → BadRequestException (400)
4. Update : is_actif = true, token = null, expires = null
5. Retourne { message: '...' }
```

## login() — aujourd'hui `LoginUseCase.execute(dto)`

```
1. Trouve l'utilisateur par email → UnauthorizedException (401) si absent
2. bcrypt.compare(password, password_hash) → UnauthorizedException si échec
3. is_actif === false → ForbiddenException (403)
4. Génère access_token (15min) et refresh_token (7j)
5. Stocke le hash du refresh token en base (saveRefreshTokenHash — met aussi à jour date_dernier_login au passage)
6. Retourne { userId, role, prenom, accessToken, refreshToken }
```

> **Changement de responsabilité :** le use case ne pose plus les cookies lui-même — il retourne les
> tokens en clair, et c'est le controller (`AuthController.login`) qui appelle `res.cookie(...)`.
> Justification : poser un cookie est une responsabilité HTTP, pas une règle métier — voir
> [[24. AuthController]].

> On retourne toujours "Email ou mot de passe incorrect" que l'email soit absent ou le mot de passe faux — pour ne pas indiquer si un email existe en base (énumération des comptes). Ce comportement n'a pas changé.

## logout() — aujourd'hui `LogoutUseCase.execute(userId)`

```
1. Efface refresh_token_hash en base
2. Ne retourne rien (void)
```

> Là aussi, `res.clearCookie(...)` (pour `access_token` et `refresh_token`) est désormais dans le controller, pas dans le use case.

## refresh() — nouveau, `RefreshTokenUseCase.execute(refreshToken)`

```
1. Vérifie la signature JWT du refresh token (secret JWT_REFRESH_SECRET) → UnauthorizedException si invalide/expiré
2. Cherche le hash stocké en base pour cet utilisateur → UnauthorizedException si absent (logout déjà effectué, token révoqué)
3. Compare le refresh token reçu au hash stocké (bcrypt.compare) → UnauthorizedException si ne correspond pas
4. Génère un nouveau access_token (15 min)
5. Retourne { accessToken }
```

N'existait pas au moment de la rédaction initiale de ce guide — ajouté avec l'endpoint `POST /auth/refresh` (voir [[28. Rafraîchissement silencieux du token JWT]]).

---

## Dépendances injectées

Chaque use case ne reçoit plus un unique `PrismaService` + `JwtService` + `EmailService` partagés,
mais uniquement ce dont il a besoin, via l'interface `IAuthRepository` :

```typescript
// register.use-case.ts
constructor(
    private readonly repo: IAuthRepository,
    private readonly emailService: EmailService,
) {}

// login.use-case.ts / refresh-token.use-case.ts
constructor(
    private readonly repo: IAuthRepository,
    private readonly jwtService: JwtService,
) {}

// confirm-email.use-case.ts / logout.use-case.ts
constructor(private readonly repo: IAuthRepository) {}
```
