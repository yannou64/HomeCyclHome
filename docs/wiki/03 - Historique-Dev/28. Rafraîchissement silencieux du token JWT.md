# 28. Rafraîchissement silencieux du token JWT

> **Statut :** Planifié — implémentation à venir (Sprint 1, mai 2026)
> **Fichiers concernés :** voir section "Fichiers à modifier"

---

## Pourquoi cette fonctionnalité ?

Le `access_token` JWT expire après **15 minutes**. Sans mécanisme de renouvellement
automatique, l'utilisateur est brutalement déconnecté à chaque expiration, même en
plein milieu d'une action. L'expérience utilisateur serait inacceptable.

Le `refresh_token` (7 jours) existe déjà et est stocké en base sous forme hashée.
Il faut maintenant brancher le circuit de renouvellement.

## Ce qui manque — le plan d'implémentation

### ÉTAPE 1 — Ajouter `findRefreshHashById` au repository

**Pourquoi une méthode dédiée ?**

`AuthUserData` (le type retourné par `findByEmail`) n'inclut pas `refresh_token_hash`.
C'est intentionnel : ce champ sensible ne doit pas circuler dans les use cases de
login, register, confirm. Une méthode dédiée fait un `SELECT` ciblé uniquement sur ce champ.

```
Interface : auth.repository.interface.ts
  findRefreshHashById(userId: string): Promise<string | null>
  → null si l'utilisateur a fait logout (champ vidé dans la base)

Implémentation : auth.prisma.repository.ts
  SELECT refresh_token_hash FROM utilisateur WHERE id = userId
```

---

### ÉTAPE 2 — Créer `RefreshTokenUseCase`

**Fichier :** `Backend/src/features/auth/use-cases/refresh-token.use-case.ts`

**Le flux complet du use case :**

```
Cookie refresh_token reçu dans la requête
        ↓
1. jwtService.verify(token, JWT_REFRESH_SECRET)
   → si invalide ou expiré → UnauthorizedException
   → si valide → payload { sub: userId, role }

2. repo.findRefreshHashById(userId)
   → si null → session révoquée (logout déjà effectué) → UnauthorizedException

3. bcrypt.compare(refreshToken, storedHash)
   → si false → token manipulé ou révoqué → UnauthorizedException

4. jwtService.sign({ sub, role }, jwtAccessConfig)
   → nouveau access_token de 15 minutes

5. res.cookie('access_token', newToken, ACCESS_COOKIE)
   → cookie réécrit, utilisateur transparent
```

**Pourquoi deux vérifications (JWT + bcrypt) ?**

La vérification JWT contrôle la **signature cryptographique** et l'**expiration**.
Mais un token JWT est valide mathématiquement même après un logout — JWT est stateless.

Le hash en base introduit une **révocation stateful** :
au logout, `clearRefreshTokenHash` efface le champ.
Si le token JWT est encore valide mais que la base ne contient plus de hash → session
révoquée. Les deux ensemble = auth stateless + révocation possible.

---

### ÉTAPE 3 — Ajouter l'endpoint `POST /auth/refresh`

**Fichier :** `Backend/src/features/auth/controllers/auth.controller.ts`

```
POST /api/auth/refresh
  ← cookie refresh_token (envoyé automatiquement par le browser, car path match)
  → appelle RefreshTokenUseCase.execute(refreshToken)
  → écrit le nouveau access_token en cookie
  → répond 200 { message: 'Token renouvelé.' }
  → répond 401 si token invalide / expiré / révoqué
```

**Pourquoi pas de `@UseGuards(JwtAuthGuard)` ?**

Le guard lit le cookie `access_token`. Sur cet endpoint, il est précisément **expiré**.
Si on y mettait le guard, il rejetterait toujours la requête avant d'arriver dans le
use case. L'authentification est portée par le refresh token lui-même, vérifié
manuellement dans le use case.

**Pourquoi le `path: '/api/auth/refresh'` sur le cookie est crucial ?**

Le browser n'envoie le cookie `refresh_token` **que** sur les requêtes vers
`/api/auth/refresh`. Sur toutes les autres routes, il n'est pas transmis.
Protection CSRF : même si une page malveillante déclenche une requête involontaire,
le refresh token n'est pas exposé hors de cet endpoint.

---

### ÉTAPE 4 — Enregistrer dans `auth.module.ts`

Ajouter `RefreshTokenUseCase` avec le même pattern `useFactory` que les autres use cases :

```ts
{
    provide: RefreshTokenUseCase,
    useFactory: (repo: AuthPrismaRepository, jwtService: JwtService) =>
        new RefreshTokenUseCase(repo, jwtService),
    inject: [AUTH_REPO, JwtService],
},
```

Et l'injecter dans le constructeur du `AuthController`.

### ÉTAPE 6 — Intercepteur Axios côté frontend

**Fichier :** `Frontend/src/shared/services/apiClient.ts`

**Principe :**
- Toute requête qui reçoit un 401 → tente un refresh silencieux via `POST /auth/refresh`
- Si le refresh réussit → rejoue la requête originale (l'utilisateur ne voit rien)
- Si le refresh échoue → logout forcé + redirection `/connexion`

**Le problème de la concurrence :**

Si 3 requêtes simultanées reçoivent un 401, sans protection les 3 déclencheraient
un refresh en même temps. Solution : file d'attente (`pendingQueue`).

```
Requête A → 401 → lance le refresh (isRefreshing = true)
Requête B → 401 → isRefreshing = true → mise en file d'attente
Requête C → 401 → isRefreshing = true → mise en file d'attente

Refresh réussit → processPendingQueue(null)
  → B et C sont rejouées avec le nouveau cookie

Refresh échoue → processPendingQueue(error)
  → B et C rejetées → logout forcé
```

**Pourquoi `window.location.href` et pas `useLogout()` ?**

L'intercepteur Axios est défini hors du contexte React (code de configuration de module).
Il n'a pas accès aux hooks. `window.location.href = '/connexion'` force un rechargement
complet qui remet `AuthContext` à zéro via `readInitialSession()` — localStorage vide
→ session null → utilisateur non authentifié.
